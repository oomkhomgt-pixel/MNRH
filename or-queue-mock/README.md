# ตัวจำลอง API ของระบบคิวห้องผ่าตัด

หน้าแฟ้มสะสมงานดึงเคสผ่าตัดจากระบบคิวได้สามทาง หนึ่งในนั้นคือ **API ของระบบจริง**
ซึ่งอยู่ใน intranet ของโรงพยาบาล เข้าถึงจากเครื่องพัฒนาไม่ได้

ตัวนี้ทำหน้าที่แทน — ตอบแบบเดียวกับที่ระบบคิวจริงตอบ เพื่อให้ทดสอบเส้นทางนำเข้าเคส
การกันนำเข้าซ้ำ การเดาผู้ร่วมผ่าตัด และการรับมือเมื่อระบบคิวมีปัญหา ได้โดยไม่ต้องรอเข้าโรงพยาบาล

```
node or-queue-mock/server.js          # เปิดที่ http://127.0.0.1:8088
PORT=9000 node or-queue-mock/server.js
```

## หน้าคอนโซล

เปิด <http://127.0.0.1:8088> ในเบราว์เซอร์ จะได้หน้าคุมตัวจำลอง ห้าแท็บ

| แท็บ | ใช้ทำอะไร |
|---|---|
| **เคสในตัวจำลอง** | ดูเคสที่มี กรองตามสถานะ/อนุสาขา/ช่วงวัน คลิกดูทุกฟิลด์ของเคสนั้นกับประวัติการแก้ไข |
| **คำขอที่เข้ามา** | เห็นสด ๆ ว่าหน้าแฟ้มถามอะไรมา ตอบรหัสอะไรกลับไป กี่เคส — ใช้ตอบว่า "ที่นำเข้าไม่ครบ เพราะถามผิดหรือเพราะข้อมูลไม่มี" |
| **ตั้งอาการเสีย** | กดปุ่มให้คำขอถัดไปพัง (500 / 401 / ไม่มีเคส / คำตอบเสีย / ช้า) โดยไม่ต้องแก้ที่อยู่ API ในหน้าแฟ้ม |
| **ฟิลด์ไหนถูกนำเข้า** | ตารางเทียบทุกฟิลด์ของเคสกับสิ่งที่ `normaliseQueueCase()` อ่านจริง — เห็นชัดว่า `patientName` ถูกทิ้ง |
| **วิธีต่อกับหน้าแฟ้ม** | ขั้นตอนตั้งค่า พร้อมที่อยู่ที่กรอกได้เลย |

แท็บ **ฟิลด์ไหนถูกนำเข้า** คือแท็บที่ใช้คุยกับคนอื่นได้ — เคสหนึ่งมี 52 ฟิลด์
หน้าแฟ้มอ่าน 20 · ขึ้นกับระดับข้อมูลผู้ป่วยที่ตั้งไว้ 3 · ไม่อ่านเลย 29 รวม `patientName`

เส้นทางที่ขึ้นต้นด้วย `/api/_mock/` มีไว้ให้หน้าคอนโซลใช้ ไม่ใช่ส่วนหนึ่งของ API ระบบคิว

แล้วที่หน้า **Logbook เคสผ่าตัด → ตั้งค่าการเชื่อมต่อ** ใส่ที่อยู่ API เป็น `http://127.0.0.1:8088`
เส้นทางปล่อยไว้ตามเดิม (`/api/cases?scope=all&includeClosed=true`) แล้วกด **ดึงจาก API**

ไม่มี dependency ตั้งใจให้รันได้ด้วย node เปล่า ๆ เหมือน `sync-server/`

## สิ่งที่ตอบกลับ

| เส้นทาง | ได้อะไร |
|---|---|
| `GET /` | หน้าคอนโซล (HTML) |
| `GET /health` | จำนวนเคสและช่วงวันที่ที่มี |
| `GET /api/cases` | `{ scope, includeClosed, count, cases:[…] }` |
| `GET /api/cases/:id` | เคสเดียว |
| `GET /api/cases/:id/history` | ประวัติการแก้ไขของเคสนั้น |
| `GET /api/auth/me` | บัญชีที่เรียก (ตัวจำลองตอบเป็นบัญชีอ่านอย่างเดียวเสมอ) |

ตัวกรอง: `scope=all|today` · `includeClosed=true|false` · `from=YYYY-MM-DD` · `to=YYYY-MM-DD` · `limit=N`

### รูปร่างของข้อมูลมาจากระบบจริง ไม่ได้เดา

หน้าสาธิตของระบบคิวที่อยู่ใน repo นี้ (`index.html` ที่ราก) ฝังข้อมูลจริงไว้ในตัวแปร
`__ORQ_SNAPSHOT__` — 755 เคส 61 ฟิลด์ ตัวจำลองถอดรูปร่างมาจากตรงนั้น จึงตรงกับของจริงในเรื่อง

| เรื่อง | ระบบจริงเป็นแบบนี้ ตัวจำลองก็ทำตาม |
|---|---|
| `id` | เป็นจำนวนเต็ม ไม่ใช่สตริง |
| `status` | มีแค่ `booked` กับ `done` (`includeClosed=false` = ตัด `done` ออก) |
| `subspecialty` | ใช้คำของระบบคิวเอง — `foot_ankle`, `tumour` (หน้าแฟ้มแปลงด้วย `QUEUE_SUB_MAP`) |
| `anesthesiaType` | เป็น `null` ได้ และเป็น `null` บ่อย (ประมาณ 1 ใน 3) |
| `asaClass` | เป็นสตริง ไม่ใช่ตัวเลข และเป็น `null` ได้ |
| `scheduledDate` / `orRoomName` | เป็น `null` ได้ — เคสที่จองแล้วแต่ยังไม่ลงวัน (จริงประมาณ 4.5%) |
| `patientName` | **ระบบคิวจริงเก็บชื่อผู้ป่วยไว้** — ดูหัวข้อถัดไป |

ฟิลด์ที่ `normaliseQueueCase()` ในหน้าแฟ้มสะสมงานอ่าน — `operationText`, `diagnosisText`,
`scheduledDate`, `orRoomName`, `primarySurgeonName`, `assistantSurgeonNames`, `operativeSide`,
`anesthesiaType`, `asaClass`, `estimatedDurationMin`, `hn`, `age`, `sex`, `complications`
— มีครบทุกตัว พร้อมฟิลด์อื่นที่ระบบจริงมีแต่หน้าแฟ้มไม่อ่าน (`readiness`, `npoStatus`,
`implants`, `procedures`, `diagnoses`, `sourceRef`, `sourceSystem`, ฟิลด์หอผู้ป่วย)

## ข้อมูลที่สร้าง

- **ผู้ป่วยเป็นข้อมูลสมมติทั้งหมด** HN ขึ้นต้นด้วย `MOCK-` ให้เห็นชัดว่าไม่ใช่ของจริง
- **มีชื่อผู้ป่วย (สมมติ) ส่งมาด้วย** ตอนแรกตัวจำลองไม่ส่งชื่อมาเลย ผลคือข้อทดสอบ
  "ไม่มีชื่อผู้ป่วยติดเข้ามา" ผ่านฟรี — ผ่านเพราะไม่มีข้อมูลให้เก็บ ไม่ใช่เพราะหน้าแฟ้มไม่เก็บ
  ตอนนี้ส่งชื่อมาเหมือนของจริง และข้อทดสอบตรวจสองชั้น: ยืนยันก่อนว่า API ส่งชื่อมาจริง
  แล้วจึงยืนยันว่าไม่มีชื่อนั้นอยู่ในเคสที่บันทึกไว้
- **ชื่อศัลยแพทย์ อนุสาขา และวันผ่าตัด อิงตารางจริงของกลุ่มงาน** เคสที่ได้จึงตกในวันที่ตรงกับ
  ตารางหมุนเวียน และการเดาผู้ร่วมผ่าตัดจากตารางทำงานเหมือนของจริง
- **สุ่มแบบกำหนดเมล็ดจากวันที่** รันกี่ครั้งก็ได้ผลเดิม ทดสอบซ้ำได้
- ช่วงวันที่ปรับได้: `DAYS_BACK` (ค่าเริ่มต้น 60) และ `DAYS_AHEAD` (14)
- `assistantSurgeonNames` เป็นรายการว่างเสมอ เพราะ **ระบบคิวจริงยังไม่บันทึกผู้ช่วยผ่าตัด** —
  จุดนี้คือเหตุผลที่หน้าแฟ้มสะสมงานต้องมีขั้นระบุผู้ร่วมผ่าตัดเอง

## จำลองอาการเสีย

ต่อท้าย query string เพื่อดูว่าหน้าเว็บรับมืออย่างไร

| พารามิเตอร์ | เกิดอะไร |
|---|---|
| `?_fail=500` | ระบบคิวตอบ error |
| `?_fail=401` | ไม่ได้รับอนุญาต |
| `?_fail=empty` | เชื่อมต่อได้ แต่ไม่มีเคส |
| `?_fail=garbage` | ตอบ JSON ที่ไม่มีเคสอยู่ข้างใน |
| `?_fail=slow` | ค้าง 30 วินาที — ใช้ดูว่าตัวจับเวลาหมดคอย 15 วินาทีทำงาน |

## ข้อจำกัด

- รูปร่างข้อมูลถอดมาจาก `__ORQ_SNAPSHOT__` ซึ่งเป็น **ข้อมูลที่ระบบคิวส่งออกมา** ไม่ใช่
  **สเปกของ API** ที่ระบบคิวประกาศ ชื่อพารามิเตอร์ของ query string การยืนยันตัวตน
  และรูปแบบ error ยังต้องทาบกับของจริงอีกที
- ระบบคิวจริงมี `/api/auth/login`, `/api/auth/logout`, `/api/auth/password`, `/api/backup`
  ตัวจำลองยังไม่ทำส่วนนั้น เพราะเส้นทางนำเข้าเคสยังไม่ได้ใช้
- ไม่มีการยืนยันตัวตน ใครเรียกก็ได้ **ใช้บนเครื่องพัฒนาเท่านั้น**
