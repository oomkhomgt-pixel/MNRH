## หน้านี้ทำอะไร

ติดตามกิจกรรมตามหลักสูตรของแพทย์ประจำบ้านแต่ละคน โดยให้ **การบันทึกเกิดขึ้นตอนที่นำเสนอสไลด์**
แทนการมานั่งกรอกย้อนหลัง

1. **รับสไลด์** — ลากไฟล์ `.pptx` หรือ `.pdf` ที่ใช้นำเสนอมาวาง หน้าเว็บจะอ่านไฟล์ในเครื่อง
   แล้วดึงชื่อเรื่อง ผู้จัดทำ วันที่สร้าง จำนวนสไลด์ และข้อความในทุกสไลด์ออกมา
2. **เดาให้ก่อน** — จากคำที่พบในสไลด์ ระบบเดา
   * **ประเภทกิจกรรม**: นำเสนอหัวข้อวิชาการ / pre-op conference / post-op conference & M&M /
     trauma film conference / journal club / ความก้าวหน้างานวิจัย
   * **อนุสาขาออร์โธปิดิกส์** (9 อนุสาขา ใช้ชื่อภาษาอังกฤษ): Orthopaedic Trauma, Spine, Arthroplasty, Sports,
     Hand & Microsurgery, Foot & Ankle, Paediatric Orthopaedics, Musculoskeletal Oncology,
     Musculoskeletal Infection
   * **ผู้นำเสนอ** จากชื่อผู้จัดทำที่ฝังอยู่ในไฟล์ เทียบกับรายชื่อแพทย์ประจำบ้าน
   พร้อมบอกว่ามั่นใจแค่ไหนและจับคำใดได้ ผู้บันทึกตรวจแล้วแก้ได้ทุกช่องก่อนกดยืนยัน
3. **เก็บเป็นหลักฐาน** — บันทึกชื่อไฟล์ จำนวนสไลด์ ข้อความที่อ่านได้ และลายนิ้วมือไฟล์ (SHA-256)
   ซึ่งใช้เตือนได้ด้วยเมื่อมีการนำไฟล์เดิมมาบันทึกซ้ำ
4. **สรุปให้เห็นส่วนขาด** — ความก้าวหน้าเทียบเกณฑ์รายชั้นปี ตารางความครอบคลุมอนุสาขารายบุคคล
   ตารางไขว้ประเภทงานนำเสนอ × อนุสาขา คลังหัวข้อที่เคยนำเสนอ ทะเบียนงานวิจัยรายขั้น
   และรายการที่ยังไม่ได้รับการรับรองจากอาจารย์
5. **ตาราง 3 แบบในหน้าเดียว** — หน้า “ตาราง: หมุนเวียน · เวร · นำเสนอ” เริ่มด้วยการ์ด *ตอนนี้ใครอยู่หน่วยไหน*
   (หน่วยที่กำลังหมุนเวียน สถานที่ อาจารย์ผู้กำกับ วันสิ้นสุดบล็อก และเซสชันของวันนี้) แล้วสลับดูได้ 3 แบบ
   * **ตารางรายเดือน** — แถวคือแพทย์ประจำบ้าน คอลัมน์คือ 12 เดือนของปีการศึกษา **เริ่ม ก.ค. จบ มิ.ย.**
     ช่องระบายสีตามหน่วยที่หมุนเวียน: สายฟ้า สายขาว สายแดง สายเหลือง, หน่วยอนุสาขา (TR/PED, HND/ONC, FT/SPT, SPN, ARP),
     การวนนอกภาควิชา (ANES, RHEU, TRS, PM&R) และ ELE = free elective · ★ = ปี 3 ที่ทำหน้าที่หัวหน้าสายในเดือนนั้น
     มีคำอธิบายสีกำกับ เลือกปีการศึกษาได้ กดที่ช่องเพื่อแก้ไขบล็อกนั้น พิมพ์และดาวน์โหลด CSV ได้
     · ปุ่ม **“สร้างแผนอัตโนมัติ”** จัดแผนทั้งปีให้ตามกติกาด้านล่าง แล้วรายงานข้อที่ยังไม่ลงตัวให้ตรวจ
     · สี ตัวย่อ ประเภทหน่วย และ subspecialty ที่หน่วยครอบคลุม แก้ได้ในหน้าตั้งค่า
   * **ตารางเวรรายสัปดาห์** — แถวคือแพทย์ประจำบ้าน คอลัมน์คือวัน แต่ละช่องคือหนึ่งเซสชัน (OR / OPD / ward round /
     conference / เวรนอกเวลา) พร้อม **อาจารย์ผู้รับผิดชอบของเซสชันนั้น** เซสชันถูกสร้างอัตโนมัติจาก *ช่วงหมุนเวียน*
     ประกอบกับ *ตารางกิจกรรมประจำสัปดาห์ของหน่วย* จึงไม่ต้องกรอกทีละวัน
   * **ตารางนำเสนอ** — ลงว่า **วันไหน ใครนำเสนอเรื่องอะไร เวลาใด ที่ห้องไหน และอาจารย์ท่านใดเป็นผู้ดำเนินการ**
     มีรายการที่กำลังจะถึง และตารางทั้งหมดพร้อมตัวกรอง แต่ละแถวมีสถานะ: ตามกำหนด / บันทึกสไลด์แล้ว /
     ยังไม่มีบันทึกสไลด์ — เมื่อวางไฟล์สไลด์เข้าระบบ ระบบจะจับคู่กับรายการในตารางให้เอง (คนเดียวกัน ประเภทเดียวกัน
     วันใกล้กันไม่เกิน 3 วัน) จึงเห็นได้ทันทีว่าการนำเสนอครั้งไหนยังไม่มีหลักฐานเก็บไว้
6. **ประเมินท้ายเซสชัน** — กดที่เซสชันใดก็ได้เพื่อบันทึกแบบประเมิน: ผู้ประเมิน (ตั้งต้นเป็นอาจารย์ผู้รับผิดชอบเซสชันนั้น),
   คะแนน 3 ด้าน (ความรู้/การตัดสินใจ, ทักษะหัตถการ, ความเป็นวิชาชีพและการสื่อสาร), ระดับการปฏิบัติงานด้วยตนเอง
   ที่ไว้วางใจได้ (entrustment 1–5) และข้อเสนอแนะทันทีหลังเซสชัน
   หน้าเดียวกันมีกระดาน **“เซสชันที่รอการประเมิน แยกตามอาจารย์ผู้รับผิดชอบ”** ย้อนหลัง 14 วัน
   เพื่อให้เห็นว่าใครยังค้างประเมินอยู่กี่เซสชัน จำนวนครั้งที่ประเมินแล้วนับรวมเป็นเกณฑ์ความก้าวหน้าของแต่ละชั้นปีด้วย
7. **พิมพ์ออกได้** — แฟ้มสะสมงานรายบุคคล (พร้อมช่องลงนาม) และรายงานหลักฐานตามมาตรฐาน WFME
   รวมถึงดาวน์โหลดเป็น CSV

## บัญชีผู้ใช้และสิทธิ์การเข้าถึง

เข้าใช้งานต้องล็อกอิน มี 3 บทบาท และเห็นข้อมูลเท่าที่จำเป็นตามบทบาท

| บทบาท | เห็นอะไร | ทำอะไรได้ |
|---|---|---|
| แพทย์ประจำบ้าน | แฟ้ม กิจกรรม logbook และ EPA **ของตนเองเท่านั้น** · ตารางหมุนเวียน/เวร/นำเสนอ ซึ่งเป็นข้อมูลส่วนรวม | บันทึกกิจกรรมของตนเอง ตั้งค่าซิงก์ของตนเอง · ประเมินไม่ได้ รับรองไม่ได้ |
| อาจารย์แพทย์ | ข้อมูลของแพทย์ประจำบ้านทุกคน เพื่อประเมินและรับรอง · หน้าความครอบคลุมและ WFME | ประเมินท้ายเซสชัน ประเมิน EPA รับรองกิจกรรม ระบุผู้ร่วมผ่าตัด นำเข้าเคส |
| ผู้จัดหลักสูตร | ทุกอย่าง | ทะเบียนผู้ใช้/อาจารย์/หน่วย ตารางหมุนเวียน เกณฑ์ หัวข้อ EPA การเชื่อมต่อ และการจัดการข้อมูล |

### อาจารย์แลกวัน OR กัน

อาจารย์นัดแลกวันกันเองเป็นครั้งคราว ตารางประจำสัปดาห์จึงไม่ตรงกับความจริงบางวัน

**ทางที่ผิดคือไปแก้ตารางประจำสัปดาห์** เพราะตารางนั้นเขียนครั้งเดียวใช้ทั้งปี แก้ทีเดียวสัปดาห์อื่นเปลี่ยนตามหมด
และคาบที่ผ่านไปแล้วจะกลายเป็นชื่ออาจารย์คนใหม่ย้อนหลัง ทั้งที่วันนั้นไม่ใช่เขา

**ทางที่ถูกคือบันทึกเป็นข้อยกเว้นของวันนั้น** ทับตารางเดิม — หลักการเดียวกับที่ตารางเวรรายเดือนใช้กับ ER
เก็บใน `store.data.swaps` แล้ว `applySwaps()` เปลี่ยนชื่อผู้รับผิดชอบตอนสร้างคาบของวันนั้น

#### การแลกเป็นคำขอ ไม่ใช่คำสั่ง

อาจารย์ฝ่ายหนึ่ง **ขอ** อีกฝ่าย **ตอบรับ** — ระหว่างรอตอบ ตารางยังเป็นชื่อเดิม เพราะยังไม่มีใครตกลงว่าจะมาแทน
`applySwaps()` มองเฉพาะรายการที่ `status === "accepted"` เท่านั้น

```
ขอ ──► pending ──► ตอบรับ ──► accepted ──► ตารางเปลี่ยน + สร้างอีกฝั่งของวันแลกกลับ
                └─► ปฏิเสธ ──► declined ──► ตารางไม่เปลี่ยน (เก็บไว้เป็นประวัติ)
```

| เรื่อง | เป็นแบบนี้ |
|---|---|
| ใครขอได้ | อาจารย์ขอได้เฉพาะคาบของตัวเอง · ผู้จัดหลักสูตรขอแทนได้ · แพทย์ประจำบ้านขอไม่ได้เลย |
| ใครตอบรับได้ | **เฉพาะฝ่ายที่ถูกขอให้มาแทน** หรือผู้จัดหลักสูตร — ผู้ขอกดตอบรับให้ตัวเองไม่ได้ |
| ระหว่างรอตอบ | ตารางยังเป็นชื่อเดิม และขึ้นป้ายว่ามีคำขอรออยู่ · ผู้ขอถอนคำขอเองได้ |
| ขอบเขต | เฉพาะวันที่ระบุ · เลือกได้ว่าทั้งวันหรือเฉพาะช่วง (เช้า/บ่าย/เต็มวัน/นอกเวลา) |
| การแสดงผล | ตอบรับแล้วขึ้นว่า **"นพ. ก (แทน นพ. ข)"** ไม่ใช่เปลี่ยนชื่อเงียบ ๆ |
| ผลประเมิน | ไม่ถูกย้าย — รหัสคาบ (`key`) ไม่มีชื่ออาจารย์อยู่ในนั้น การแลกจึงเปลี่ยนแค่ชื่อผู้รับผิดชอบ ไม่ได้เปลี่ยนตัวคาบ |
| แลกกลับ | ใส่วันที่แลกกลับไว้ อีกฝั่งถูกสร้าง **ตอนตอบรับ** ไม่ใช่ตอนขอ จึงเป็นการ **แลก** ไม่ใช่การ **ฝาก** |
| กันชนกัน | ถ้าคนที่ถูกขอมีคาบอื่นในวันนั้นอยู่แล้ว ระบบเตือนทั้งตอนขอและตอนตอบรับ |

คำขอที่รอตอบโผล่ที่หน้า **วันนี้** ของอาจารย์ที่ถูกขอ พร้อมปุ่มตอบรับ/ปฏิเสธ และเตือนถ้าวันนั้นเขาติดคาบอื่นอยู่

ขอได้สามทาง: ปุ่ม **+ ขอแลกวัน** ที่การ์ด "การแลกวัน OR ของอาจารย์" ในหน้าตาราง ·
ปุ่ม **ขอแลกวันนี้** บนการ์ดคาบของตัวเองในหน้า "วันนี้" · หรือเปิดคาบนั้นในปฏิทินแล้วกดจากในกล่อง

#### แพทย์ประจำบ้านไม่ย้ายตาม

แพทย์ประจำบ้านอยู่กับ **สายของตัวเองในเดือนนั้น** เสมอ — คนที่แลกคือคนลงมือผ่าตัด ไม่ใช่ทั้งทีม
การแลกวันจึงเปลี่ยนแค่ชื่ออาจารย์ที่มาคุมลิสต์นั้น ไม่ย้ายใครข้ามสาย มีข้อทดสอบยืนยันไว้

วันที่คนในสายไม่พอ **หัวหน้าสายเป็นคนตัดสินหน้างาน ไม่ได้กำหนดล่วงหน้า** ระบบจึงไม่มีช่องให้วางแผนเรื่องนี้ไว้ก่อน
แต่คำสั่งของหัวหน้าสาย**ไม่ใช่การอนุมัติ** — ดูหัวข้อถัดไป

### ประเมินครั้งเดียว ได้ทั้งผลประเมินท้ายเซสชันและระดับ EPA

แบบประเมินท้ายเซสชันกับการประเมิน EPA ใช้สเกล entrustment **เดียวกัน** (`ENTRUST_LEVELS` 1–5)
เดิมเป็นสองงานแยกกัน อาจารย์ที่ประเมินท้ายเซสชันแล้วต้องไปให้ระดับ EPA อีกรอบที่หน้า EPA — ให้ระดับเดิมซ้ำสองครั้ง

ตอนนี้ในแบบประเมินท้ายเซสชันมีช่องติ๊ก **หัวข้อ EPA ที่คาบนี้ครอบคลุม** หัวข้อที่ตรงกับอนุสาขาของคาบนั้นถูกยกขึ้นมาก่อน
(ติดดาว) ติ๊กแล้วกดบันทึกครั้งเดียว ระบบเขียนทั้งผลประเมินท้ายเซสชันและผลประเมิน EPA ให้พร้อมกัน

| เรื่อง | เป็นแบบนี้ |
|---|---|
| ค่าที่ใช้ | ระดับ entrustment ที่ให้ในแบบประเมินนั้นเอง — ถ้าไม่ได้ให้ระดับ ก็ไม่เขียน EPA |
| ที่มา | ผล EPA เก็บ `sessionKey` ไว้ หน้า EPA จึงบอกได้ว่าระดับนี้มาจากคาบไหน |
| แก้ผลประเมิน | ผล EPA ของคาบนั้นถูกเขียนทับ ไม่เกิดรายการซ้อน |
| ลบผลประเมิน | ผล EPA ที่มาจากคาบนั้นถูกลบตามไปด้วย ไม่เหลือระดับที่ไม่มีที่มา |
| ประเมิน EPA แยกต่างหาก | ยังทำได้ตามเดิมที่หน้า EPA สำหรับหัวข้อที่ไม่ได้ผูกกับคาบใดคาบหนึ่ง |

### ปฏิบัติงานนอกสาย/นอกหน่วย — ต้องได้รับอนุมัติเสมอ

กติกาของกลุ่มงาน: **ทุกครั้งที่ปฏิบัติงานนอกสาย/นอกหน่วยของตัวเอง ต้องได้รับอนุมัติจากอาจารย์ผู้กำกับ**
ไม่มีข้อยกเว้น ไม่ว่าจะด้วยเหตุผลใด

| เหตุผล | ใครเป็นคนเริ่ม |
|---|---|
| หัวหน้าสายมอบหมายหน้างาน — คนในสายไม่พอ | หัวหน้าสายตัดสินหน้างาน **แล้วยังต้องมีคำขอให้อาจารย์อนุมัติ** |
| เคสที่เกี่ยวกับงานวิจัยที่ทำอยู่ | แพทย์ประจำบ้าน |
| เคสที่หาดูยาก / น่าสนใจทางวิชาการ | แพทย์ประจำบ้าน |
| ตามเก็บหัตถการที่ยังขาดตามเกณฑ์ | แพทย์ประจำบ้าน |

**คำสั่งของหัวหน้าสายไม่ใช่การอนุมัติ** หัวหน้าสายเป็นแพทย์ประจำบ้านด้วยกัน มีอำนาจจัดคนหน้างาน
แต่การรับรองว่าใครปฏิบัติงานที่ไหนเป็นของอาจารย์ เพราะเป็นสิ่งที่เอาไปนับเป็นผลการฝึกอบรม
เรื่องที่เกิดไปแล้วขอย้อนหลังได้ ระบบกำกับป้าย **“ขอย้อนหลัง”** ไว้ให้ผู้อนุมัติเห็นว่ากำลังอนุมัติสิ่งที่เกิดไปแล้ว

```
แพทย์ประจำบ้านขอ ──► รออนุมัติ ──► อนุมัติ ──► คาบนั้นขึ้นในตาราง คาบของสายเดิมที่ชนกันกลายเป็นคาบที่ไม่ได้เข้า
                              └─► ไม่อนุมัติ ──► ตารางไม่ขยับเลย (เก็บไว้เป็นประวัติ)
```

`computeSessions()` สร้างคาบนี้เฉพาะคำขอที่ `status === "approved"` — **ก่อนอนุมัติ คาบนั้นไม่มีอยู่ในตารางเลย**
ระบบไม่บันทึกสิ่งที่ยังไม่ได้รับอนุญาต

| เรื่อง | เป็นแบบนี้ |
|---|---|
| ใครขอได้ | เจ้าของตารางเอง (หรือผู้จัดหลักสูตร) — ขอแทนคนอื่นไม่ได้ |
| **ใครอนุมัติได้** | อาจารย์ผู้กำกับของช่วงหมุนเวียนนั้น ถ้าไม่ได้ระบุไว้ ก็คือ**อาจารย์ที่มีคาบกับสายของเขาในวันนั้น** — คนใดคนหนึ่งอนุมัติก็พอ · ผู้จัดหลักสูตรอนุมัติได้เสมอ · **ผู้ขออนุมัติให้ตัวเองไม่ได้** |
| ลำดับความสำคัญ | เท่ากับการเลือกเข้าคาบรายวัน (35) — ชนะงานบริการตามตาราง แต่ **ยังแพ้กิจกรรมวิชาการ (40)** เพราะวิชาการมาก่อนเสมอ |
| เหตุผล | เลือกจากรายการ (หัวหน้าสายมอบหมายหน้างาน · งานวิจัย · เคสที่หาดูยาก · ตามเก็บหัตถการ · อื่น ๆ) “อื่น ๆ” ต้องระบุรายละเอียด |
| ขอย้อนหลัง | ทำได้ และติดป้ายไว้ให้ผู้อนุมัติเห็น — ไม่ใช่การแอบบันทึกทีหลัง |
| การแสดงผล | คาบนั้นติดป้าย **“ได้รับอนุมัติให้ไปเข้าคาบสายอื่น”** พร้อมเหตุผล ไม่ใช่โผล่มาเฉย ๆ |
| ประเมิน | คาบนี้มีรหัสของตัวเอง อาจารย์สายที่ไปเข้าประเมินท้ายเซสชันได้ตามปกติ |

คำขอที่รออนุมัติโผล่ที่หน้า **วันนี้** ของอาจารย์ผู้อนุมัติ · แพทย์ประจำบ้านเห็นสถานะคำขอของตัวเองในหน้า **วันนี้** เช่นกัน

#### ทางลัดที่ปิดไว้

**การเข้าคาบรายวัน** (`sessionPicks`) บันทึกได้แค่ว่าวันนั้นเข้าคาบไหน *ในบรรดาคาบของตัวเอง* และระบุอาจารย์ได้
เฉพาะคนที่อยู่ในตารางของตัวเองวันนั้น — ระบุอาจารย์นอกสายตรงนั้นไม่ได้ ไม่งั้นมันจะกลายเป็นทางลัด
บันทึกการปฏิบัติงานนอกสายโดยไม่ผ่านการอนุมัติ มีข้อทดสอบยืนยันว่าทางลัดนี้ปิดจริง

### หน้า "วันนี้" — หน้าแรกสำหรับมือถือ

หน้าอื่นทั้งหมดตอบว่า "ภาพรวมเป็นอย่างไร" หน้านี้ตอบแค่ "ตอนนี้ฉันต้องไปไหน มีอะไรค้าง"
จึงไม่มีตารางใหญ่ เหลือเฉพาะสิ่งที่กดได้จากมือถือขณะยืนอยู่หน้าห้องผ่าตัด
เนื้อหาต่างกันตามบทบาท เพราะคำว่า "วันนี้" ของสามบทบาทไม่ใช่เรื่องเดียวกัน

| บทบาท | เห็นอะไร |
|---|---|
| แพทย์ประจำบ้าน | สายที่อยู่วันนี้ · คาบของตัวเองเรียงตามเวลา (คาบที่ระบุเวลามาก่อน แล้วค่อยคาบเต็มวัน) · เตือนเมื่อมีกิจกรรมวิชาการ · เตือนเมื่อมีคาบชนกันที่ต้องเลือกเอง · เคสห้องผ่าตัดของวันนั้นที่เกี่ยวกับหน่วยตัวเอง · กิจกรรมที่ยังรออาจารย์รับรอง |
| อาจารย์แพทย์ | คาบที่ระบุชื่อตัวเองไว้ พร้อมรายชื่อแพทย์ประจำบ้านในคาบนั้น กดประเมินได้ทันที · เซสชันของตัวเองที่ค้างประเมิน 14 วันย้อนหลัง |
| ผู้จัดหลักสูตร | วันนี้ใครอยู่สายไหน · เซสชันค้างประเมิน · กิจกรรมรอรับรอง · คนที่วันนี้ไม่มีคาบเลย · คนที่ยังไม่ได้กำหนดช่วงหมุนเวียน |

เดินวันย้อนหลัง/ไปข้างหน้าได้ด้วยปุ่ม ‹ › แต่เปิดหน้าใหม่ทีไรก็กลับมาเป็นวันนี้เสมอ
แพทย์ประจำบ้านและอาจารย์เข้าระบบแล้วมาถึงหน้านี้เป็นหน้าแรก ผู้จัดหลักสูตรยังเริ่มที่หน้ารับสไลด์ตามเดิม

### งานนำเสนอแยกตามประเภท × อนุสาขา

หน้า **ความครอบคลุมอนุสาขา** เดิมตอบได้ทีละคำถาม: เลือกประเภทหนึ่ง แล้วดูตาราง
*แพทย์ประจำบ้าน × อนุสาขา* ซึ่งบอกว่าใครยังขาดอนุสาขาไหน แต่บอกไม่ได้ในภาพเดียวว่า
**pre-op conference ของทั้งกลุ่มงานกระจุกอยู่ที่อนุสาขาใด** และ **อนุสาขาใดยังไม่เคยถูกหยิบมาทำ
conference ชนิดนั้นเลย**

จึงเพิ่มการ์ด *งานนำเสนอ แยกตามประเภท × อนุสาขา* — แถวคือประเภทงานนำเสนอ
(pre-op conference, post-op conference / M&M, topic, trauma film, journal club, ความก้าวหน้างานวิจัย)
คอลัมน์คือ 9 อนุสาขา ช่องคือจำนวนงานนำเสนอ

- ไล่**เฉดสีเดียว**จากอ่อนไปเข้ม เพราะช่องนี้วัด *ขนาด* ไม่ใช่แยก *ตัวตน*
  (ถ้าใช้หลายสีจะอ่านเป็นหมวดหมู่ ทั้งที่มันคือมาก–น้อย)
- **ช่องที่เป็นศูนย์ทำสีต่างหาก** เป็นแดงอ่อนพร้อมเครื่องหมาย ✕ ไม่ปล่อยให้จางหายไปกับพื้น
  เพราะศูนย์คือสิ่งที่เปิดตารางนี้มาหา
- ตารางนี้**นับทุกประเภทเสมอ** ไม่ขึ้นกับตัวกรองประเภทด้านบน (ไม่งั้นจะไม่เหลืออะไรให้อ่านไขว้)
  แต่ยึดตามปีการศึกษาที่เลือก
- การ์ดเดียวกันนี้อยู่ใน**แดชบอร์ดที่ส่งออก**ด้วย และวาดจากฟังก์ชันเดียวกัน (`typeSubTableHtml`)
  ตัวเลขบนจอกับในไฟล์จึงเพี้ยนจากกันไม่ได้ — มีข้อทดสอบยืนยันไว้

### แดชบอร์ดส่งออก

ปุ่ม **แดชบอร์ด** บนแถบบน (และในหน้าความครอบคลุม) สร้างไฟล์ `dashboard-YYYY-MM-DD.html`

**ไฟล์เดียวจบ ไม่มีสคริปต์ ไม่มีไลบรารี ไม่อ้าง asset จากภายนอก** — เปิดได้แม้ไม่มีเน็ต
ส่งทางอีเมลได้ เก็บเข้าแฟ้มได้ และสั่งพิมพ์เป็น PDF ลง A4 แนวนอนได้ กราฟเป็น SVG เขียนตรง ๆ

| ส่วน | ตอบคำถามอะไร |
|---|---|
| ตัวเลขหัวเรื่อง | มีกี่คน กิจกรรมปีนี้เท่าไร เคสเท่าไร **ค้างประเมินกี่เซสชัน** |
| ความก้าวหน้าเทียบเกณฑ์ | **ใครตามหลังมากที่สุด** — หนึ่งแถวต่อคน เรียงแย่สุดขึ้นก่อน แยกตามชั้นปี |
| สิ่งที่ยังขาด | 10 คนแรกที่ต้องตาม พร้อมบอกว่าขาดอะไร |
| กิจกรรมรายเดือน | กิจกรรมกระจุกเดือนไหน แยกตามประเภท |
| เคสแยกอนุสาขา | อนุสาขาไหนมีเคสน้อย |
| EPA | หัวข้อไหนเฉลี่ยต่ำกว่าเป้าหมายของชั้นปี |
| **งานนำเสนอ ประเภท × อนุสาขา** | pre-op conference กระจุกอยู่ที่อนุสาขาใด และอนุสาขาใดยังไม่เคยถูกหยิบมาทำ conference เลย |
| ตารางตัวเลข | ตัวเลขชุดเดียวกับกราฟ สำหรับคนที่อยากอ่านค่าตรง ๆ |

**สิทธิ์:** ได้ข้อมูลเท่าที่บัญชีนั้นมองเห็น — แพทย์ประจำบ้านได้แดชบอร์ดของตัวเองคนเดียว
อาจารย์และผู้จัดหลักสูตรได้ทั้งกลุ่มงาน มีข้อทดสอบยืนยันว่าไม่มีชื่อคนอื่นหลุดเข้าไป

**ไม่มีข้อมูลผู้ป่วยรายบุคคลในไฟล์นี้** — เป็นตัวเลขรวมทั้งหมด ไม่มี HN ไม่มีชื่อ ไม่มีวันผ่าตัดรายเคส
จึงเป็นไฟล์ส่งออกชนิดเดียวที่ส่งต่อในที่ประชุมได้โดยไม่ต้องระวังเป็นพิเศษ

สีของกราฟชุดหมวดหมู่ผ่านการตรวจการมองเห็นสีบกพร่องแล้ว (ΔE ต่ำสุดของคู่ที่อยู่ติดกัน 9.1)
และทุกกราฟมีตัวเลขกำกับพร้อมตารางเดียวกันท้ายไฟล์ — สีจึงไม่ใช่ทางเดียวที่อ่านค่าได้

ต่างกันตรงที่ชื่อของแฟ้มสะสมงานอยู่ใน **แถบทึบสีน้ำเงินเขียว** ส่วนของระบบคิวเป็นข้อความเปล่า

เหตุผลที่ต้องมีแถบ ไม่ใช่แค่เปลี่ยนคำ: **ที่ 48px ตัวอักษรอ่านไม่ออกแล้วทั้งคู่**
ถ้าต่างกันแค่คำ สองไอคอนจะเหลือเป็นรอยเปื้อนเล็ก ๆ ใต้โลโก้เดียวกัน แยกไม่ออก
แถบทึบเป็นสิ่งเดียวที่ยังเห็นได้ทุกขนาด

```bash
CHROMIUM_PATH=/path/to/chrome node portfolio/docs/make-icons.mjs
```

สร้างครบทั้งสี่ใบจาก `logo-lockup.png` — เปลี่ยนคำบนแถบได้ที่ตัวแปร `LABEL` ในสคริปต์
`icon-maskable-512.png` ย่อทั้งก้อนเข้ามา 12% ให้ทั้งโลโก้และแถบรอดจากการครอปเป็นวงกลมและ squircle ของ Android

### รหัสสาธิตของแต่ละบทบาท

รหัสแยกตามบทบาท เพื่อให้สลับบทบาทแล้วเห็นว่าสิทธิ์ต่างกันจริง ไม่ใช่แค่เปลี่ยนชื่อที่มุมจอ

| บทบาท | บัญชี | รหัส |
|---|---|---|
| ผู้จัดหลักสูตร | `admin` | `9001` |
| อาจารย์แพทย์ | `staff1`–`staff23` | `2001`–`2023` |
| แพทย์ประจำบ้าน | `resident1`–`resident20` | `3001`–`3020` |

สูตรคือเลขนำหน้าตามบทบาท ต่อด้วยเลขบัญชีสองหลัก — `staff7` ใช้ `2007` · `resident12` ใช้ `3012`
ที่หน้าเข้าสู่ระบบมีปุ่มเติมรหัสให้ตอนสาธิต ข้อมูลเก่าที่ยังใช้รหัส `1234` จะถูกย้ายให้อัตโนมัติตอนเปิดครั้งถัดไป

**นี่คือรหัสสาธิต ไม่ใช่ระบบยืนยันตัวตน** การตรวจสิทธิ์ทั้งหมดทำในเบราว์เซอร์ ใครเปิด devtools ก็อ่านได้
ของจริงต้องผูกกับบัญชีของโรงพยาบาลและตรวจสิทธิ์ที่เซิร์ฟเวอร์

- ทุกการเข้าใช้ ประเมิน รับรอง นำเข้า และสร้างแผน ถูกบันทึกใน **ร่องรอยการใช้งาน** (500 รายการล่าสุด) ดูได้ที่หน้าตั้งค่า

### เส้นแบ่งสิทธิ์ที่บังคับไว้จริงในโค้ด

ข้อมูลทั้งภาควิชาอยู่ใน localStorage ก้อนเดียวกันของเครื่องที่ดึงข้อมูลจากคลาวด์มา
การกรองตามบทบาทจึงต้องครบทุกทาง ไม่ใช่เฉพาะหน้าที่นึกออก จุดที่บังคับไว้มีดังนี้

| ทาง | ใครทำได้ | บังคับที่ |
|---|---|---|
| ส่ง/ดึง **ข้อมูลทั้งชุด** ขึ้น-ลงคลาวด์ | ผู้จัดหลักสูตร | `cloudPush()` / `cloudPull()` และ `syncMode()` ที่ตกกลับเป็นโหมด logbook ให้บัญชีอื่น |
| ตั้งที่อยู่ปลายทางการซิงก์ | ผู้จัดหลักสูตร | `syncSettingsDialog()` — บัญชีอื่นได้หน้าอ่านอย่างเดียวที่แสดงเฉพาะรายการของตนเอง |
| ส่งออก/นำเข้าไฟล์ข้อมูลทั้งชุด | ผู้จัดหลักสูตร | `exportJson()` / `importJson()` + `data-perm="admin"` ที่ปุ่ม |
| เปิด/แก้กิจกรรม | เจ้าของกิจกรรม และอาจารย์ | `openActivity()` · `applyActivityEdits()` · `savePending()` |
| ย้ายกิจกรรมไปเป็นของคนอื่น | ผู้จัดหลักสูตร | `applyActivityEdits()` |
| ให้คะแนน/ข้อเสนอแนะ | อาจารย์ | `applyActivityEdits()` — เจ้าของกิจกรรมแก้คะแนนตัวเองไม่ได้ |
| ติ๊ก "อาจารย์รับรอง" ในเคสผ่าตัด | อาจารย์ | `editCaseParticipants()` — ช่องถูกปิดและค่าเดิมถูกคงไว้แม้แก้ DOM ตรง ๆ |
| ระบุบทบาทของตัวเองในเคส | เจ้าของแถวนั้น และอาจารย์ | `editCaseParticipants()` — แถวที่แก้ไม่ได้จะถูกคงไว้ทั้งแถว ไม่เขียนทับกันข้ามคน |
| ลบเคสออกจาก logbook | ผู้จัดหลักสูตร | `editCaseParticipants()` |
| แก้ทะเบียนแพทย์ประจำบ้าน / บัญชีผู้ใช้ | ผู้จัดหลักสูตร | `editResident()` / `editUser()` |

- **logbook เป็นของรายบุคคลเสมอ** — ถ้ายังไม่ได้ระบุว่าเป็นของใคร `syncPayloadItems()` จะส่งรายการเปล่า
  (เดิมช่องว่างแปลว่า "ทุกเคสในเครื่อง" ซึ่งเผลอส่งเคสของคนอื่นออกไปได้)
- **ข้อความจากสไลด์ถูกล้างก่อนเก็บ** — `scrubPatientText()` ตัดสิ่งที่ดูเหมือน HN เลขบัตรประชาชน
  เลขเวชระเบียน และชื่อที่ขึ้นต้นด้วยคำนำหน้าออก ก่อนบันทึกเป็นหลักฐานของกิจกรรม
  (การเดาประเภท/อนุสาขาทำจากข้อความเต็มไปแล้วก่อนถึงขั้นนี้ จึงไม่กระทบความแม่น)
- **ไฟล์สำรองคือฐานข้อมูลทั้งก้อน** รวมข้อมูลผู้ป่วยใน logbook และรหัสผ่านของบัญชี
  เก็บในดิสก์ของภาควิชาเท่านั้น ไม่ส่งต่อทางอีเมลหรือแชท — หน้าเว็บถามยืนยันก่อนดาวน์โหลดทุกครั้ง
- **ข้อจำกัดที่ต้องรู้**: การตรวจสิทธิ์ทั้งหมดอยู่ในเบราว์เซอร์ จึงเป็นการ *แบ่งมุมมองและกันแก้ผิดคน* บนเครื่องที่ใช้ร่วมกัน
  **ยังไม่ใช่การยืนยันตัวตนเชิงความปลอดภัย** — ของจริงต้องผูกกับบัญชีของโรงพยาบาลและตรวจสิทธิ์ที่เซิร์ฟเวอร์
  โครงนี้แยกชั้นไว้แล้ว (`currentUser()` / `canSeeResident()` / `canAssess()` / `canManage()`) จึงเปลี่ยนไปใช้ session
  ของเซิร์ฟเวอร์ได้โดยไม่ต้องรื้อหน้าอื่น

## การประเมิน EPA

- หน้า **EPA** แสดงหัวข้อแยกตามอนุสาขา พร้อม **ระดับล่าสุด** เทียบ **เป้าหมายของชั้นปีนั้น** และประวัติการประเมินย้อนหลัง
- อาจารย์กดประเมินได้จากในหน้า: เลือกระดับ 1–5 (ชุดเดียวกับ entrustment ท้ายเซสชัน) ผูกกับเคสผ่าตัดได้ และใส่ข้อสังเกต
- อาจารย์เห็นตารางภาพรวมทั้งกลุ่มงาน (แพทย์ประจำบ้าน × หัวข้อ) สีเขียวคือถึงเป้าหมายของชั้นปีแล้ว
- ผู้จัดหลักสูตรแก้หัวข้อและตั้งเป้าหมายรายชั้นปีได้ที่หน้าตั้งค่า

> **หัวข้อ EPA ที่ใส่มาให้ตอนนี้เป็นตัวอย่างสำหรับวางโครงเท่านั้น ยังไม่ใช่รายการจริง**
> เมื่อได้รายการจริงของกลุ่มงาน ให้นำเข้าทับได้ทันที — CSV คอลัมน์ `code, title, subspecialty, year1..year4`
> หรือ JSON `[{code, title, subspecialty, targets:{1..4}}]` (ส่งออกไฟล์ตัวอย่างจากปุ่มข้าง ๆ ได้)
> การนำเข้าจะแทนที่หัวข้อเดิมทั้งชุด และล้างผลประเมินที่อ้างหัวข้อเก่าออกไปด้วย

## ใช้เป็นแอปบนมือถือ และเป็นเว็บแอปพร้อมกัน

หน้านี้เป็น **PWA** แล้ว — โค้ดชุดเดียวใช้ได้ทั้งบนเบราว์เซอร์และติดตั้งเป็นแอปบนมือถือ

| อุปกรณ์ | วิธีติดตั้ง |
|---|---|
| Android (Chrome/Edge) | กดปุ่ม **“ติดตั้งแอป”** มุมขวาบน หรือเมนู ⋮ → ติดตั้งแอป |
| iPhone / iPad (Safari) | ปุ่มแชร์ → **เพิ่มไปยังหน้าจอโฮม** (iOS ไม่มีปุ่มติดตั้งอัตโนมัติ) |
| คอมพิวเตอร์ | ใช้ในเบราว์เซอร์ได้เลย หรือกดไอคอนติดตั้งในแถบที่อยู่ |

เมื่อติดตั้งแล้วจะเปิดเต็มจอ มีไอคอนของตัวเอง และ **ใช้งานได้แม้ไม่มีสัญญาณ** เพราะหน้าเว็บถูกเก็บไว้ในเครื่อง
ด้วย service worker และข้อมูลอยู่ใน localStorage อยู่แล้ว · เงื่อนไข: ต้องเสิร์ฟผ่าน **https** หรือ **localhost**
(เปิดไฟล์ตรง ๆ แบบ `file://` จะติดตั้งไม่ได้) · หน้า “ตั้งค่า &amp; ข้อมูล” มีปุ่ม **ตรวจการเชื่อมต่อ**
ที่บอกสถานะการติดตั้ง การทำงานออฟไลน์ และสาเหตุเมื่อต่อระบบคิวไม่ได้

**ถ้าต้องการเป็นแอปใน store หรือแจกผ่าน MDM ของโรงพยาบาลจริง ๆ** ห่อไฟล์ชุดนี้ด้วย Capacitor ได้โดยไม่ต้องเขียนใหม่

```bash
npm create @capacitor/app@latest ortho-portfolio     # แล้วคัดลอกไฟล์ในโฟลเดอร์นี้ไปไว้ใน www/
npm i @capacitor/android @capacitor/ios
npx cap add android && npx cap add ios
npx cap sync && npx cap open android                 # build เป็น .apk / .ipa ต่อจากนี้
```

ข้อดีที่ได้เพิ่มจากการห่อเป็นแอป native คือคำขอเครือข่ายวิ่งผ่าน native HTTP layer จึง**ไม่ติดกฎ CORS และ
mixed content ของเบราว์เซอร์** ซึ่งเป็นอุปสรรคหลักเมื่อระบบคิวอยู่ใน intranet (ดูตารางถัดไป)

## เชื่อมกับระบบคิวที่อยู่ใน intranet ได้ไหม

ได้ แต่ผลลัพธ์ขึ้นกับว่า **หน้านี้ถูกวางไว้ที่ไหน** เพราะเบราว์เซอร์บังคับกฎ 2 ข้อ: หน้า https เรียก http ไม่ได้
(mixed content) และการเรียกข้ามโดเมนต้องได้รับอนุญาตจากปลายทาง (CORS)

| วางหน้า portfolio ไว้ที่ | ดึงเคสจากระบบคิว | ข้อควรรู้ |
|---|---|---|
| **เซิร์ฟเวอร์เดียวกับระบบคิวใน intranet** (แนะนำที่สุด) เช่น `https://or-queue.hospital.local/portfolio/` | ได้ทันที เรียก `/api/cases` แบบ same-origin | ไม่ต้องตั้ง CORS ไม่ติด mixed content และใช้ session ที่ผู้ใช้ล็อกอินระบบคิวไว้แล้ว |
| เครื่องแม่ข่ายอื่นใน intranet ที่เป็น **https** | ได้ ถ้าระบบคิวส่ง `Access-Control-Allow-Origin` เป็นโดเมนนี้ และ `Access-Control-Allow-Credentials: true` | ต้องแก้ตั้งค่าฝั่งระบบคิว |
| เครื่องแม่ข่ายอื่นใน intranet ที่เป็น **http** | ได้ ถ้าหน้านี้ก็เป็น http เหมือนกัน | แต่ http จะติดตั้งเป็นแอป (service worker) ไม่ได้ |
| **GitHub Pages** (https สาธารณะ) | **เรียกระบบคิวที่เป็น http ใน intranet ไม่ได้** เบราว์เซอร์บล็อกเพราะ mixed content | ใช้ทางนำเข้าไฟล์ JSON/CSV แทน หรือย้ายไปโฮสต์ใน intranet |
| **แอป native (Capacitor)** | เรียกตรงได้ ข้าม CORS/mixed content | เครื่องต้องอยู่ในวง intranet หรือ VPN ของโรงพยาบาล |
| ไม่เชื่อมเลย | export JSON/CSV จากระบบคิว → นำเข้าที่หน้า Logbook | ใช้ได้เสมอ ไม่ต้องแก้อะไรฝั่งระบบคิว |

**ทดสอบโดยไม่ต้องต่อ intranet**: มี [ตัวจำลอง API ของระบบคิว](../or-queue-mock/) อยู่ในที่เก็บนี้
เปิดด้วย `node or-queue-mock/server.js` แล้วตั้งที่อยู่ API เป็น `http://127.0.0.1:8088`
เคสที่สร้างอิงตารางจริงของกลุ่มงาน (ศัลยแพทย์ อนุสาขา วันผ่าตัด) การเดาผู้ร่วมผ่าตัดจึงทำงานเหมือนของจริง
และจำลองอาการเสียได้ด้วย (`?_fail=500|401|empty|garbage|slow`) เพื่อดูว่าหน้าเว็บบอกสาเหตุถูกหรือไม่

สรุปที่ใช้ได้จริงที่สุดสำหรับสถานการณ์ “ระบบคิวเป็นเว็บแอปใน intranet”: **วางไฟล์หน้านี้ไว้บนเซิร์ฟเวอร์เดียวกับระบบคิว**
แล้วให้แพทย์ประจำบ้านติดตั้งจากที่อยู่ intranet นั้นลงมือถือ เวลาอยู่ในโรงพยาบาล (ต่อ wifi โรงพยาบาลหรือ VPN)
จะดึงเคสได้ตรง ๆ ส่วนเวลาอยู่นอกโรงพยาบาลยังเปิดแอปดูและบันทึกได้ตามปกติ เพียงแต่ดึงเคสใหม่ไม่ได้จนกว่าจะกลับเข้าวง

หน้าตั้งค่าการเชื่อมต่อมีสวิตช์ **“ไม่บันทึก HN ลงเครื่องนี้”** สำหรับกรณีติดตั้งบนโทรศัพท์ส่วนตัว
เมื่อเปิดไว้ HN จะไม่ถูกเก็บลงเครื่องเลย (ทั้งข้อมูลเดิมและที่นำเข้าใหม่)

## ควรวางระบบอย่างไรเมื่อ OR queue อยู่ใน intranet แต่ผู้ใช้ต้องใช้จากนอกโรงพยาบาล

ข้อเสนอ: **แยกเป็นสองโซน** และให้ intranet ถูกใช้เฉพาะตอนดึงข้อมูลเคสเท่านั้น

- **โซนนอก** — แฟ้มสะสมงานสำหรับแพทย์ประจำบ้านและอาจารย์ (ติดตั้งเป็นแอปได้ ใช้จากที่บ้านได้ ไม่ต้อง VPN)
- **โซนใน** — ระบบคิวห้องผ่าตัดอยู่ที่เดิม ไม่ต้องเปิดออกสู่อินเทอร์เน็ต

ตัวเชื่อมระหว่างสองโซนเลือกได้ 3 แบบ เรียงจากที่แนะนำ

1. **ให้ผู้ใช้ดึงเองตอนอยู่ในโรงพยาบาล** (ทำได้แล้ววันนี้ ไม่ต้องแก้อะไรฝั่งระบบคิว)
   เปิดแอปตอนต่อ wifi โรงพยาบาล กดดึงเคส ระบบเก็บเฉพาะข้อมูลที่ตั้งระดับไว้ · ไม่ต้องเปิดพอร์ตใด ๆ ออกนอก
   ข้อจำกัดคือต้องอยู่ในวงและต้องกดเอง
2. **สคริปต์ซิงก์ขาเดียวจากข้างใน** (แนะนำถ้าจะทำระบบกลาง) — โปรแกรมเล็ก ๆ รันในโรงพยาบาล ดึงเคสจากระบบคิว
   → ตัดข้อมูลผู้ป่วยออก → ส่งขึ้นเซิร์ฟเวอร์ของแฟ้มสะสมงานผ่าน HTTPS **ขาออกอย่างเดียว**
   ไม่ต้องเปิด inbound ให้ intranet เลย และแพทย์ประจำบ้านเห็นเคสได้โดยไม่ต้องอยู่ในโรงพยาบาล
3. **เปิดระบบคิวออกนอกผ่าน VPN หรือ reverse proxy** — ไม่แนะนำ เพราะเพิ่มพื้นที่เสี่ยงให้ระบบที่มีข้อมูลผู้ป่วยจริง

**สิ่งที่ควรระวังเรื่อง PDPA** ถ้าเซิร์ฟเวอร์ของแฟ้มสะสมงานอยู่นอกโรงพยาบาล

- อย่านำ **ชื่อผู้ป่วยและ HN** ออกไป — ใช้ระดับ “ไม่เก็บข้อมูลผู้ป่วยเลย” ในหน้าตั้งค่าการเชื่อมต่อ
  (เก็บเฉพาะ diagnosis / operation / บทบาท / วันที่) แล้วอ้างอิงกลับด้วยเลขที่เคสของระบบคิวซึ่งไม่มีความหมายนอกโรงพยาบาล
- ถ้าจำเป็นต้องมี HN เพื่อตรวจสอบย้อนกลับ ให้เก็บไว้เฉพาะในเครื่องผู้ใช้หรือในวง intranet เท่านั้น
- ระบบกลางควรมี: ล็อกอินผูกกับบัญชีโรงพยาบาล, สิทธิ์ตามบทบาท (ผู้เข้าฝึกอบรม / อาจารย์ / ผู้จัดหลักสูตร),
  บันทึกการเข้าถึง, การสำรองข้อมูล, กำหนดอายุการเก็บ และเอกสาร ROPA/DPIA ตามที่โรงพยาบาลใช้อยู่

**ลำดับที่แนะนำให้ทำ**

1. *ตอนนี้* — ใช้แบบไฟล์เดียวต่อเครื่องไปก่อน ดึงเคสตอนอยู่ในโรงพยาบาล พิสูจน์ว่ากระบวนการเวิร์กกับกลุ่มงานจริง
2. *ขั้นถัดไป* — เพิ่มเซิร์ฟเวอร์กลางเล็ก ๆ (ผู้ใช้ + สิทธิ์ + ซิงก์) วางใน DMZ ของโรงพยาบาล ผูกกับบัญชีเดิม
   ทั้งแอปอ่านเขียนผ่านชั้น `store` ชั้นเดียว จึงต่อซิงก์ได้โดยไม่ต้องรื้อหน้าอื่น
3. *เมื่อพร้อม* — เพิ่มสคริปต์ซิงก์ขาเดียวจากข้างใน เพื่อให้ logbook เต็มโดยไม่ต้องรอให้ผู้ใช้กดเอง

## ซิงก์ logbook ขึ้นระบบกลางอัตโนมัติ

หน้า Logbook มีปุ่ม **“ซิงก์ระบบกลาง”** ตั้งที่อยู่ปลายทาง เลือกว่าเป็น logbook ของใคร แล้วระบบจะส่งให้เอง —
ส่งตอนเปิดแอป ตอนมีการแก้ไข (รวบไว้ 5 วินาทีแล้วส่งครั้งเดียว) ทุก 10 นาทีถ้ายังค้าง และทันทีที่กลับมาออนไลน์
มีป้ายสถานะบนแถบบน (ซิงก์แล้ว / รอซิงก์ / กำลังซิงก์)

**ข้อมูลที่ส่งออกมีเพียง 3 อย่าง: วันที่ผ่าตัด, diagnosis, operation** (บวก `role` ถ้าผู้ใช้เลือกเปิด)
ไม่มี HN ไม่มีชื่อผู้ป่วย ไม่มีอายุ/เพศ ไม่มีชื่อศัลยแพทย์ · หน้าตั้งค่าจะแสดง **ตัวอย่าง JSON จริงที่จะถูกส่ง**
ให้ตรวจก่อนเปิดใช้

สัญญาข้อมูล: `PUT {url}` รับ `{user, updatedAt, items[]}` และ `GET {url}?user=…` คืน `{items[]}`
มีเซิร์ฟเวอร์อ้างอิงพร้อมทดลองอยู่ที่ [`sync-server/`](../sync-server/) ซึ่ง **ตัดฟิลด์ที่ไม่ได้ตกลงกันทิ้งอีกชั้นหนึ่ง**
ก่อนบันทึก ของจริงควรเพิ่มเส้นทางนี้เข้าไปในเซิร์ฟเวอร์ของระบบคิวที่มีระบบผู้ใช้อยู่แล้ว

## ฐานข้อมูลกลาง 2 ทาง: คลาวด์ของภาควิชา + ดิสก์ของภาควิชา

**ทางที่ 1 — คลาวด์ของภาควิชา (ฐานข้อมูลกลางที่ใช้งานร่วมกัน)**

- เลือกโหมด **“ฐานข้อมูลกลางของภาควิชา — ส่งข้อมูลทั้งชุด”** ในหน้าซิงก์ แล้วใส่ที่อยู่คลาวด์
- ส่งขึ้นอัตโนมัติเหมือนเดิม (ตอนเปิดแอป · 5 วินาทีหลังแก้ไข · ทุก 10 นาทีถ้าค้าง · เมื่อกลับมาออนไลน์)
- ส่งทั้งชุด: ทะเบียนแพทย์ประจำบ้าน/อาจารย์/หน่วย ตารางหมุนเวียน เซสชันและผลประเมิน กิจกรรม งานวิจัย logbook EPA เกณฑ์ และข้อมูลหลักสูตร
  · **ไม่ส่งรหัสผ่านของบัญชี** และเมื่อดึงกลับมา รหัสเดิมในเครื่องยังใช้ล็อกอินได้
- ปุ่ม **“ดึงข้อมูลทั้งชุดจากคลาวด์”** ใช้ตอนตั้งเครื่องใหม่หรือกู้คืน โดยจะบอกก่อนว่าจะทับด้วยข้อมูลชุดไหน อัปเดตล่าสุดเมื่อไร จากเครื่องใด
- ฝั่งเซิร์ฟเวอร์อ้างอิงเก็บ **เวอร์ชันย้อนหลัง 10 รุ่น** (`GET …/dataset?versions=1` ดูรายการได้)

**ทางที่ 2 — สำรองลงดิสก์ของภาควิชา**

- ที่หน้าตั้งค่า เลือกโฟลเดอร์บนดิสก์ของภาควิชาไว้ครั้งเดียว (Chrome/Edge บนคอมพิวเตอร์) ระบบจำสิทธิ์ไว้ให้
- กด **“สำรองลงโฟลเดอร์ตอนนี้”** หรือปล่อยให้สำรองเองเมื่อถึงกำหนด (ตั้งได้ว่ากี่วันครั้ง) — ชื่อไฟล์ตามวันเวลา
  หมุนไฟล์เก่าออกตามจำนวนที่ตั้งไว้ และมีประวัติการสำรองให้ตรวจ
- ถ้าเบราว์เซอร์เขียนโฟลเดอร์ไม่ได้ (Safari, มือถือ) ใช้ปุ่มดาวน์โหลดแล้วเก็บไฟล์เองได้ ระบบยังนับเป็นการสำรองและบันทึกประวัติให้
- มีคำเตือนเมื่อเลยกำหนดสำรอง และกู้คืนจากไฟล์ได้จากปุ่มเดียวกัน

**ข้อควรทำเมื่อใช้จริง**

- ยึดหลัก 3-2-1: ข้อมูลหลักบนคลาวด์ · สำเนาบนดิสก์ภาควิชา · และควรมีอีกชุดเก็บคนละที่ตั้ง
- **ทดสอบกู้คืนจริงเป็นระยะ** อย่างน้อยปีละครั้ง — ไฟล์สำรองที่ไม่เคยลองกู้คืนไม่นับว่าเป็นการสำรอง
- ดิสก์ที่ใช้สำรองควรเข้ารหัสทั้งลูก และบัญชีคลาวด์ควรมีผู้ดูแลมากกว่าหนึ่งคน เผื่อคนเดียวลาออกหรือติดต่อไม่ได้
- ไฟล์สำรองมีข้อมูลทั้งหมดที่เครื่องนั้นเก็บ รวมถึง logbook — ถ้าตั้งระดับข้อมูลผู้ป่วยเป็น “เก็บ HN” ไฟล์สำรองก็จะมี HN ด้วย
  ให้เลือกระดับให้ตรงกับที่ตกลงกับโรงพยาบาล และเก็บไฟล์สำรองในที่ที่คุมการเข้าถึงได้
### กันการแก้พร้อมกันทับกัน

ทำไว้ 3 ชั้น ทำงานร่วมกัน

1. **เซิร์ฟเวอร์นับรุ่น (revision) และปฏิเสธของที่ล้าสมัย** — ทุกครั้งที่ส่งขึ้น เครื่องต้องบอกว่าแก้มาจากรุ่นไหน
   ถ้ามีคนอื่นส่งขึ้นไปก่อนจนรุ่นไม่ตรง เซิร์ฟเวอร์ตอบ **409 พร้อมส่งของปัจจุบันกลับมา** แทนที่จะยอมให้เขียนทับ
2. **รวมข้อมูลแบบสามทางที่ฝั่งเครื่อง** — แต่ละเครื่องเก็บ *ฐาน* ไว้ = ชุดข้อมูลตอนซิงก์สำเร็จครั้งล่าสุด
   เมื่อชนกันจึงเทียบได้ว่า **อะไรคือสิ่งที่เครื่องนี้แก้จริง** แล้วเอาเฉพาะส่วนนั้นไปวางทับบนของคลาวด์
   รายการที่เราไม่ได้แตะจะไม่ทับของคนอื่น จากนั้นส่งใหม่อัตโนมัติด้วยรุ่นล่าสุด
   · การลบก็เทียบกับฐานเช่นกัน ของที่เราลบจะไม่ถูกปลุกกลับมา และถ้าเครื่องอื่นเพิ่งแก้รายการที่เราลบ ระบบจะคงของเขาไว้แล้วบันทึกไว้ให้ตรวจ
3. **บันทึกรายการที่ชนกันจริง** — เฉพาะกรณีที่ *รายการเดียวกัน* ถูกแก้ทั้งสองฝั่ง ระบบจะเก็บฉบับของเครื่องที่ส่งทีหลัง
   แล้วลงรายการไว้ที่หน้าตั้งค่า (ส่วนข้อมูล / รายการ / เวลา / ผลที่เลือก) เพื่อให้คนตรวจย้อนได้ ไม่ใช่หายเงียบ

ผลที่ได้ (ทดสอบด้วยสองเครื่องพร้อมกัน)

| สถานการณ์ | ผลลัพธ์ |
|---|---|
| สองเครื่องแก้ **คนละรายการ** | รวมกันได้ทั้งคู่ ไม่มีอะไรหาย ไม่ถือเป็นการชนกัน |
| สองเครื่องแก้ **รายการเดียวกัน** | เก็บฉบับของเครื่องที่ส่งทีหลัง + บันทึกรายการที่ชนกันไว้ให้ตรวจ |
| เครื่องหนึ่งลบ อีกเครื่องแก้รายการอื่น | การลบมีผล และการแก้ของอีกเครื่องยังอยู่ |
| เครื่องหนึ่งลบ อีกเครื่องแก้ **รายการที่ถูกลบ** | คงของที่ถูกแก้ไว้ก่อน แล้วบันทึกไว้ให้คนตัดสิน |

**ลดการชนกันตั้งแต่ต้นด้วยการแบ่งความเป็นเจ้าของ** — สิทธิ์ที่ตั้งไว้ช่วยอยู่แล้ว: ทะเบียนและตารางแก้ได้เฉพาะผู้จัดหลักสูตร
ผลประเมินเป็นของอาจารย์ผู้ประเมิน และบันทึกของแพทย์ประจำบ้านแต่ละคนแยกกัน โอกาสที่สองคนแก้ *รายการเดียวกัน* พร้อมกันจึงเหลือน้อยมาก

**ยังไม่ได้ทำ (ควรทำเมื่อขึ้นระบบจริง)** — รวมข้อมูลระดับ *ฟิลด์* ในรายการเดียวกัน, ส่งเฉพาะรายการที่เปลี่ยน (delta) แทนทั้งชุด,
ล็อกเชิงแนะนำเวลาแก้ตารางทั้งผืน และเก็บประวัติการแก้รายรายการไว้ที่เซิร์ฟเวอร์เพื่อย้อนกลับได้ทีละรายการ

## ความสัมพันธ์กับระบบ logbook ของราชวิทยาลัย

ระบบของราชวิทยาลัยเป็น **ที่บันทึกอย่างเป็นทางการ** และต้องแนบฟิล์มกับ operative note ซึ่งเจ้าตัวต้องลงเอง
หน้านี้จึง **ไม่ทำ logbook ซ้อน** และไม่เก็บฟิล์มหรือ op note

บทบาทของหน้านี้คือ **ตัวเตรียมข้อมูลและตัวจับตก**

- ดึงเคสจากระบบคิวมาให้ครบ แล้วระบุบทบาทของแต่ละคนในไม่กี่คลิก (ข้อมูลที่ระบบคิวมีอยู่แล้วไม่ต้องพิมพ์ซ้ำ)
- ทำเครื่องหมาย **“ลงระบบราชวิทยาลัยแล้ว”** รายเคส เพื่อให้เห็นว่าเหลือค้างกี่เคส — มีตัวกรอง “ยังไม่ได้ลงราชวิทยาลัย”
  และปุ่มทำเครื่องหมายทีเดียวทั้งชุดที่กรองไว้
- พิมพ์ **“ใบกรอกราชวิทยาลัย”** เฉพาะเคสที่ยังไม่ได้ลง เรียงตามวันที่ พร้อมช่องติ๊ก เพื่อนั่งกรอกรวดเดียว
- นับจำนวนเคสตามบทบาทเข้าเกณฑ์ของหลักสูตร และใช้เป็นหลักฐาน WFME ในภาพรวมของกลุ่มงาน

ถ้าวันหนึ่งราชวิทยาลัยเปิด API ให้ส่งข้อมูลเข้าโดยตรง ก็ต่อเพิ่มจากจุดนี้ได้ทันที เพราะข้อมูลถูกจัดรูปไว้แล้ว

## ข้อมูลยังแยกกันคนละเครื่อง

ต้องรู้ก่อนตัดสินใจ: ตอนนี้ข้อมูลเก็บใน **เบราว์เซอร์ของแต่ละเครื่อง** ไม่ได้แชร์กัน — แพทย์ประจำบ้านบันทึกในมือถือตัวเอง
อาจารย์เปิดในคอมพิวเตอร์จะไม่เห็นข้อมูลนั้น ย้ายข้อมูลได้ด้วยไฟล์สำรอง JSON เท่านั้น

ถ้าต้องการให้ทุกคนเห็นข้อมูลชุดเดียวกัน (แพทย์ประจำบ้านบันทึก อาจารย์รับรอง ผู้จัดหลักสูตรดูภาพรวม)
ต้องมี **ฐานข้อมูลกลาง** เพิ่มเข้ามา ทางที่สมเหตุสมผลที่สุดคือฝากไว้กับเซิร์ฟเวอร์ของระบบคิวที่มีอยู่แล้ว
เพราะมีระบบผู้ใช้ สิทธิ์ และการบันทึกตาม PDPA อยู่แล้ว โดยเพิ่ม API ประมาณ
`GET/POST /api/portfolio/{residents,activities,rotations,sessions,cases}` แล้วให้หน้านี้ซิงก์ขึ้นลง
ส่วนที่เหลือของแอปไม่ต้องแก้ เพราะทุกอย่างอ่าน–เขียนผ่านชั้น `store` ชั้นเดียว

## เชื่อมกับระบบคิวห้องผ่าตัดเพื่อลง logbook

หน้า **“Logbook เคสผ่าตัด”** ดึงรายการเคสจากระบบคิวห้องผ่าตัดมาใช้เป็นสมุดบันทึกการผ่าตัดของแพทย์ประจำบ้าน
ต่อได้ 3 ทาง เลือกทางที่ตรงกับการติดตั้งจริง

1. **อ่านจากหน้าระบบคิวในที่เก็บเดียวกัน** — กดปุ่มเดียว หน้านี้จะอ่าน `../index.html` (หน้าสาธิตระบบคิว)
   ดึงข้อมูลเคสที่ฝังอยู่ในหน้านั้นออกมา ใช้ได้เมื่อเปิดผ่าน GitHub Pages หรือเว็บเซิร์ฟเวอร์
   (เปิดจาก `file://` เบราว์เซอร์จะไม่ยอมให้อ่านไฟล์ข้างเคียง)
2. **นำเข้าไฟล์** — JSON ที่ export จากระบบคิว หรือ CSV ที่มีหัวคอลัมน์
   `date, hn, diagnosis, operation, subspecialty, surgeon, assistant, room, anesthesia, asa, side, duration, id`
3. **ต่อ API ของระบบจริง** — ตั้งที่อยู่ระบบคิวในหน้าตั้งค่าการเชื่อมต่อ ระบบจะเรียก
   `GET {ที่อยู่}/api/cases?scope=all&includeClosed=true` พร้อม cookie ของผู้ใช้ (ต้องล็อกอินระบบคิวอยู่ และฝั่งระบบคิวต้องอนุญาต CORS)
   หน้านี้ไม่เก็บรหัสผ่านหรือโทเคนใด ๆ

เคสซ้ำจะถูกอัปเดตทับ ไม่สร้างรายการซ้ำ (จับคู่ด้วยเลขที่เคสของระบบคิว) และ **ชื่อผู้ป่วยไม่ถูกนำเข้ามาโดยตั้งใจ**
สิ่งที่นำเข้าคือ วันที่ HN อายุ เพศ การวินิจฉัย การผ่าตัด ข้าง อนุสาขา ห้อง ประเภทเคส การระงับความรู้สึก ASA
ระยะเวลา และชื่อศัลยแพทย์หลัก · HN แสดงแบบปิดบังไว้ก่อน กดเปิดดูเต็มได้เมื่อต้องตรวจสอบ

### ใครร่วมผ่าตัดเคสไหน

ข้อจำกัดที่ต้องรู้: **ระบบคิวรุ่นปัจจุบันบันทึกเฉพาะศัลยแพทย์หลัก ยังไม่มีช่องผู้ช่วยผ่าตัด**
(ในข้อมูลสาธิต `assistantSurgeonNames` ว่างทุกเคส) หน้านี้จึงเติมชั้น “ผู้ร่วมผ่าตัด” ให้เอง โดย

- จับคู่ชื่อที่มีอยู่ในเคส (ศัลยแพทย์หลัก ผู้ช่วย ผู้ลงข้อมูล) กับรายชื่อแพทย์ประจำบ้านให้อัตโนมัติ
- ถ้าจับคู่ไม่ได้ **เสนอชื่อจากตารางหมุนเวียน** — ใครหมุนเวียนอยู่หน่วยที่ตรงกับอนุสาขาของเคสในวันนั้น
  กดปุ่มเดียวเพื่อเติมทั้งหมด แล้วค่อยไล่แก้บทบาททีหลัง
- บทบาทที่บันทึกได้: ผู้ผ่าตัดหลัก / ผู้ช่วยที่ 1 / ผู้ช่วยที่ 2 / ผู้สังเกตการณ์ พร้อมช่องให้อาจารย์รับรอง

จำนวนเคสแยกตามบทบาทนับรวมเป็นเกณฑ์ความก้าวหน้าของแต่ละชั้นปี (ตั้งค่าได้) แสดงในแฟ้มรายบุคคล
และพิมพ์เป็น logbook รายคนได้ (สรุปตามอนุสาขา + รายการเคสเรียงลำดับ + ช่องลงนามอาจารย์ผู้รับรอง)

**ถ้าอยากให้อัตโนมัติเต็มรูปแบบ** ระบบคิวต้องเพิ่มการบันทึกผู้ร่วมผ่าตัดในเคส เช่นฟิลด์
`attendees: [{ userId, role }]` หรือเติมชื่อลง `assistantSurgeonNames` ให้ครบ เมื่อมีข้อมูลนั้นแล้ว
หน้านี้จะจับคู่ให้เองทันทีโดยไม่ต้องยืนยันทีละเคส

## กติกาการจัดหมุนเวียนที่ระบบใช้

ปีการศึกษาเริ่ม **1 กรกฎาคม** จบ **30 มิถุนายน** แบ่งเป็น 12 บล็อก บล็อกละ 1 เดือน

| ชั้นปี | การหมุนเวียน |
|---|---|
| ปี 1 | วนนอกภาควิชา 3 เดือน — วิสัญญีวิทยา, โรคข้อ (rheumatology), ศัลยกรรมอุบัติเหตุ อย่างละ 1 เดือน · ที่เหลือวนตามสาย |
| ปี 2 | เวชศาสตร์ฟื้นฟู (PM&R) 1 เดือน · ที่เหลือวนตามสาย |
| ปี 3 | วนตามสาย + free elective 3 เดือน (ไปพร้อมกันได้ไม่เกิน 2 คน) · ทำหน้าที่หัวหน้าสายเมื่อสายนั้นไม่มีปี 4 |
| ปี 4 | วนหน่วยอนุสาขา**ให้ครบทุกหน่วย**ก่อน · เดือนที่เหลือเป็นกำลังเสริมให้สายที่ขาด **สายละไม่เกิน 1 เดือน และไม่จำเป็นต้องลงสายจนครบ** · ตั้งแต่ มี.ค. เป็น free elective พร้อมกันทั้งชั้นปีถึง มิ.ย. |

เงื่อนไขเพิ่มเติมที่ตัวจัดแผนพยายามรักษา

- การวนนอกภาควิชาของชั้นปีเดียวกัน **ไม่ให้ชนกัน** (ไม่เกิน ⌈จำนวนคนในชั้นปี ÷ 3⌉ คนต่อเดือน)
- การลงสาย **แบ่งจำนวนคนให้เท่ากันที่สุด** ในแต่ละเดือน และเลี่ยงการอยู่สายเดิมสองเดือนติด
- **คุมองค์ประกอบรุ่นในสาย** — เกลี่ยรุ่นพี่ (ปี 3–4) และรุ่นน้อง (ปี 1–2) แยกกัน ไม่ให้สายใดมีแต่รุ่นน้องหรือมีแต่รุ่นพี่
  ถ้าสายใดไม่มีรุ่นพี่ ระบบจะย้ายปี 3 จากสายที่มีรุ่นพี่เกินมาให้ก่อน
- **ปี 4 เป็นกำลังเสริม** — ระบบจะกันเดือนให้ครบทุกหน่วยอนุสาขาก่อนเสมอ เดือนที่เหลือจึงถูกจัดไปช่วยสายที่ว่าง
  หรือสายที่ไม่มีรุ่นพี่ โดย **สายละไม่เกิน 1 เดือนต่อคน** ถ้าไม่มีสายไหนขาดก็ไม่ต้องลงสาย (ได้อยู่หน่วยอนุสาขาต่อ)
  และในเดือนเดียวกันปี 4 จะไม่ซ้ำหน่วยอนุสาขากันเอง

หน้าตารางรายเดือนมีตาราง **“องค์ประกอบของแต่ละสาย”** อยู่ใต้ตารางหลัก แสดงจำนวนคนในสายแต่ละเดือนพร้อมสัดส่วน
ปี 3–4 / ปี 1–2 ทำสีให้เห็นทันทีว่าเดือนไหนสายว่าง ไม่มีรุ่นพี่ หรือรุ่นน้องกระจุก

ตรวจแล้วทุกขนาดรุ่น: ปี 4 ทุกคน**วนครบทั้ง 5 หน่วยอนุสาขา** และ**ไม่เคยลงสายเดิมซ้ำ**

ผลทดสอบกับขนาดรุ่นต่าง ๆ (48 ช่อง = 4 สาย × 12 เดือน)

| ขนาดรุ่น | สายว่าง | สายที่ไม่มีรุ่นพี่ | ขนาดสายเฉลี่ย | ปี 4 ได้ sub/สาย/elective |
|---|---|---|---|---|
| ชั้นปีละ 2 คน (8) | 0 | 24 | 1.3 | 5 / 3 / 4 เดือน |
| ชั้นปีละ 3 คน (12) | 0 | 13 | 2.0 | 5–6 / 2–3 / 4 |
| ชั้นปีละ 4 คน (16) | 0 | 3 | 2.6 | 5–6 / 2–3 / 4 |
| ชั้นปีละ 5 คน (20) | 0 | 0 | 3.1 | 6–7 / 1–2 / 4 |

ยิ่งรุ่นใหญ่ยิ่งลงตัว ส่วนรุ่นเล็กมากจะมีบางเดือนที่สายมีแต่รุ่นน้อง ซึ่งเป็นข้อจำกัดของจำนวนคนจริง ๆ
ระบบจึงรายงานออกมาให้ผู้จัดตารางตัดสินใจ แทนที่จะซ่อนไว้
- หน่วยอนุสาขาที่อยู่คู่กัน: **Trauma/Paediatrics · Hand/Tumour · Foot & Ankle/Sports** ส่วน Spine และ Arthroplasty แยกหน่วย
- ไม่มีการวน ER เป็นบล็อกแยก (งานห้องฉุกเฉินอยู่ในเวรของแต่ละสาย)

ปุ่ม “สร้างแผนอัตโนมัติ” สร้างแผนทั้งปีตามกติกานี้ แล้วรายงานสิ่งที่ยังไม่ลงตัว เช่น เดือนที่สายใดไม่มีคนลง
หรือเดือนที่ elective เต็มเพดาน เพื่อให้ผู้จัดตารางแก้เองต่อได้ (ทุกบล็อกยังกดแก้ทีละช่องได้ตามปกติ)

## ตารางประจำสัปดาห์: ส่วนกลาง + หน่วย + สาย

ตารางของแต่ละคนไม่ได้เขียนทีละคน แต่เกิดจากสามชั้นซ้อนกัน แล้วระบบคูณกับ**ตารางหมุนเวียน**ให้เอง

| ชั้น | ใครได้ | ตัวอย่าง |
|---|---|---|
| **ส่วนกลางของภาควิชา** | ทุกคน ไม่ว่าเดือนนั้นอยู่หน่วยไหน | morning report, grand round, journal club |
| **หน่วยที่วนอยู่** | คนที่อยู่หน่วยนั้นในเดือนนั้น | OR ของหน่วย trauma, OPD ของสายฟ้า |
| **หน่วยอนุสาขา** | คนที่วน sub — **หน่วยอนุสาขาไม่มีตารางของตัวเอง งานแบ่งไปอยู่ในสาย** คนวน sub จึงตามลิสต์ของอนุสาขาตัวเองในทุกสาย | R4 วน hand/tumour ตาม OR hand ของสายฟ้า/แดง/เหลือง และ OR tumour ของสายแดง/เหลือง |
| **ตารางเวรรายเดือน** | คนที่ตารางเวรของเดือนนั้นระบุไว้ | อยู่เวร ER, วันหยุดราชการ |

- **เขียนครั้งเดียวใช้ทั้งปี** — 10 หน่วย × ~5 คาบ ≈ 50 บรรทัด แทนที่จะเขียน 8 คน × 5 คาบ × 48 สัปดาห์ ≈ 2,000 บรรทัด
  และเมื่อมีคนสลับสาย ไม่ต้องแตะตารางเลย เพราะตารางหมุนเวียนจัดการให้
- **หนึ่งคาบมีอาจารย์ได้หลายคน** เพราะสายหนึ่งมีอาจารย์จากหลายอนุสาขาปนกัน
  ตอนประเมินท้ายคาบจึงเลือกได้ว่าใครเป็นผู้ประเมินจริงในวันนั้น
- **คาบส่วนกลางจำกัดชั้นปีได้** (เช่น inter-hospital conference เฉพาะปี 4) และเลือกได้ว่าคนที่วนนอกภาควิชาต้องเข้าด้วยหรือไม่
- **คาบของอาจารย์ล้วน** ติดธง `staffOnly` ไว้ได้ — อยู่ในตารางเป็นบันทึก แต่ไม่สร้างคาบให้แพทย์ประจำบ้าน
  (คลินิกพิเศษออร์โธเด็กบ่ายพฤหัสบดีไม่มีแพทย์ประจำบ้านเข้า จึงไม่ได้อยู่ในตารางนี้เลย
  ดูได้ที่ทะเบียนอาจารย์แทน)

### เมื่อคาบชนกัน

- คาบที่ **ไม่ระบุเวลา** = ใช้ทั้งช่วง (OR ทั้งเช้า) · คาบที่ **ระบุเวลา** = แทรกอยู่ในช่วงนั้น (ประชุม 07:30–08:30)
- ถือว่าชนกันเมื่อ **ทั้งคู่ใช้ทั้งช่วงเดียวกัน** หรือ **เวลาที่ระบุคาบเกี่ยวกัน** —
  ถ้าอันหนึ่งระบุเวลาอีกอันไม่ระบุ ไม่นับว่าชน ไม่งั้นประชุมเช้าจะขึ้นว่าชนกับ ward round ทุกวันซึ่งไม่จริง
- ตัดสินด้วย **ลำดับความสำคัญ** ตั้งได้ที่หน้าตั้งค่า ค่าเริ่มต้น
  **กิจกรรมวิชาการ 40** · ส่วนกลาง 30 · ตารางเวรรายเดือน 25 · หน่วยอนุสาขา 20 · สาย 10
  และแต่ละคาบตั้งตัวเลขเฉพาะของตัวเองทับได้
- **กิจกรรมวิชาการเป็นหน้าที่แรกของแพทย์ประจำบ้าน มาก่อนงานบริการเสมอ** — คาบที่ติดธง `academic`
  ได้ลำดับสูงสุด และการบันทึกรายวันก็ชนะได้แค่คาบงานบริการด้วยกัน ไม่ชนะกิจกรรมวิชาการ
  (เช่น ปี 4 ต้องเข้า inter-hospital conference บ่ายพฤหัสบดีเสมอ)
- คาบที่แพ้ **ยังแสดงอยู่ในปฏิทิน** แบบเส้นประและจาง พร้อมบอกว่าไปชนกับอะไร — ไม่ซ่อน เพราะคนจัดตารางต้องเห็น
  และไม่ถูกนับเป็นงานค้างประเมินของอาจารย์
- **ถ้าลำดับเท่ากัน ระบบจะไม่ตัดสินแทน** แต่ทำเครื่องหมายว่าชนกันเพื่อให้คนเลือกเอง

### ตารางเวรรายเดือน — ของที่ไม่ซ้ำทุกสัปดาห์

บางอย่างเขียนเป็นตารางสัปดาห์ไม่ได้ เพราะเปลี่ยนทุกวันหรือทุกสัปดาห์ ตรงนี้จึงเป็นชั้นที่สี่
อยู่ที่แท็บ **ตาราง** ลงเป็นรายวันของวันราชการ

| ช่อง | ใช้ทำอะไร |
|---|---|
| OPD (สาย) | สายที่ออกตรวจวันนั้น |
| OPD (อาจารย์) | วันพฤหัสบดีลงเป็นชื่ออาจารย์แทนสาย |
| ER (สาย) | สายที่อยู่เวรวันนั้น — วันพฤหัสบดีวนไปเรื่อย ไม่ตายตัวเหมือนวันอื่น |
| อาจารย์เวร | อาจารย์เวรของวันนั้น เปลี่ยนทุกวัน |
| แพทย์ประจำบ้านที่อยู่เวร | ระบุตัวได้ ถ้าไม่ระบุจะตกกับทุกคนที่อยู่สายนั้น |
| หยุด | วันหยุดราชการ |

- **“เติมจากรูปแบบประจำสัปดาห์”** กรอกวันจันทร์–ศุกร์ให้ก่อน โดยอ่านจากตารางของแต่ละสายเอง
  (สายไหนมี OPD วันไหน สายไหนมี OR emergency วันไหน) แล้วค่อยแก้เฉพาะวันที่ต่างออกไป
  วันพฤหัสบดีเว้นว่างไว้ เพราะไม่มีรูปแบบตายตัวให้เดา
- **ER ในเวลาราชการเป็นความรับผิดชอบของทั้งสาย** ไม่ใช่ของคนใดคนหนึ่ง ทุกคนในสายได้คาบนี้
- **คนที่ชั้นปีน้อยที่สุดเป็นหน้างาน** — คนแรกที่เจอเคสและรับ consult จากนอกแผนก
  แต่ **ไม่ใช่ผู้ตัดสินใจหลัก** ผู้ตัดสินใจคืออาจารย์ผู้รับผิดชอบของวันนั้น
  ระบุตัวเองได้ที่ช่อง “หน้างาน” ถ้าเว้นว่างระบบจะเลือกคนที่ชั้นปีน้อยที่สุดให้
- คาบ ER เป็น **การบอกหน้าที่ ไม่ใช่การบอกที่อยู่** จึงติดธง `advisory` ไม่เข้าไปนับว่าชนกับคาบไหน
  ทุกคนในสายยังเข้า OR emergency ตามตารางประจำสัปดาห์ได้ตามปกติ
- **วันหยุดลบคาบตามตารางประจำสัปดาห์ทิ้งทั้งวัน** แต่คงสิ่งที่ตารางเวรระบุไว้เอง เพราะวันหยุดก็ยังต้องมีคนอยู่เวร
- แก้ได้เฉพาะผู้จัดหลักสูตร และทุกการแก้เขียนร่องรอยการใช้งาน

### เลือกเป็นรายวันว่าเข้าคาบไหน กับอาจารย์คนใด

ลำดับความสำคัญเป็นกติกาของทั้งปี แต่ของจริงบางวันไม่เป็นไปตามนั้น — โดยเฉพาะคนที่วนตามสาย
ซึ่งมักไม่ได้ชนกันเป็นระบบ แค่ต้องเลือกว่าวันนี้ไปห้องไหน กับอาจารย์คนไหน

- เปิดคาบใดก็ได้ในปฏิทิน แล้วกด **“บันทึกว่าเข้าคาบนี้”** พร้อมเลือกอาจารย์ผู้คุมของวันนั้น
- **การเลือกรายวันชนะลำดับความสำคัญของงานบริการ** และมีผลเฉพาะวันนั้น ไม่กระทบสัปดาห์อื่น — แต่ไม่ชนะกิจกรรมวิชาการ
- คาบอื่นในช่วงเดียวกันของวันนั้นจะขึ้นว่า “วันนี้เลือกเข้า …” แยกจากกรณีที่แพ้เพราะลำดับความสำคัญ
- **เจ้าของตารางบันทึกเองได้** ไม่ต้องรออาจารย์ แต่บันทึกแทนคนอื่นไม่ได้ (อาจารย์และผู้จัดหลักสูตรทำแทนได้)
- อาจารย์ที่เลือกไว้จะถูกใช้เป็นผู้ประเมินตั้งต้นของคาบนั้น

## ชุดทดสอบและการตรวจอัตโนมัติ

`</script>` หลุดเข้าไปในโค้ด ซึ่งปิดบล็อกสคริปต์กลางคันและทำให้ทั้งแอปตาย ชุดทดสอบจึงมีไว้จับเรื่องนี้
และเรื่องที่สำคัญกว่า คือกันไม่ให้การแก้ครั้งต่อ ๆ ไปเผลอเปิดช่องสิทธิ์ที่ปิดไปแล้วกลับมาอีก

```
npx playwright install chromium         # ครั้งแรกครั้งเดียว
node run.mjs                            # รันทุกชุด
```

## ข้อจำกัดที่ต้องรู้ก่อนใช้

- **ข้อมูลอยู่ในเบราว์เซอร์ของเครื่องที่เปิดเท่านั้น** (localStorage) ไม่มีเซิร์ฟเวอร์ ไม่มีการรับส่งข้อมูลออกนอกเครื่อง
  เปิดคนละเครื่องจะไม่เห็นข้อมูลของกัน ใช้ปุ่มสำรอง/นำเข้าไฟล์ JSON เพื่อย้ายข้อมูล
- **ไม่ได้เก็บตัวไฟล์สไลด์** เก็บเฉพาะข้อความที่อ่านได้ ชื่อไฟล์ และค่าแฮช ต้นฉบับต้องเก็บไว้ที่อื่นตามระบบของกลุ่มงาน
- `.pptx` อ่านได้ครบที่สุด ส่วน `.pdf` อ่าน metadata ได้เสมอ แต่เนื้อความในสไลด์อ่านได้บ้างไม่ได้บ้าง
  ขึ้นกับวิธีฝังฟอนต์ (ภาษาไทยใน PDF มักอ่านไม่ออก) หน้าเว็บจะบอกเมื่ออ่านไม่ได้และให้กรอกเอง
- การเดาประเภทและอนุสาขาเป็นการช่วยกรอก ไม่ใช่คำตัดสิน ผู้บันทึกต้องตรวจก่อนยืนยันเสมอ
- ข้อมูลตัวอย่างทั้งหมดเป็นข้อมูลสมมติ ไม่มีชื่อบุคคลจริงและไม่มีข้อมูลผู้ป่วย

## For readers of this repository

A **demonstration page only**: one self-contained HTML file, no backend, no build step, no external
assets, no network requests. It tracks orthopaedic residents' training activities — topic presentations,
pre-/post-operative conferences, trauma film conferences, journal clubs and research progress.

The point of it is that recording happens *when the resident presents*: drop the `.pptx`/`.pdf` used for
the presentation onto the page and it is parsed in the browser (zip + OOXML for `.pptx`, object/stream
parsing for `.pdf`) to recover the title, author, creation date, slide count and slide text. Keyword
scoring over that text proposes the activity type and the orthopaedic subspecialty; the person recording
checks and confirms. The file's SHA-256 is kept as an evidence fingerprint and for duplicate detection —
the file itself is never uploaded or stored.

Every activity is tagged with the WFME postgraduate-standard sub-areas it can serve as evidence for, so
the programme can print an evidence report per standard area and per resident. The standards skeleton
follows the 9 areas of the WFME Global Standards for Quality Improvement (PGME, 2015 revision) but has
**not been reconciled word-for-word with the official document** — verify before using it for real
accreditation. All demo data is fictitious.

A second half of the page answers *where is each resident right now*, in three tables. A **monthly grid**
(residents x the 12 blocks of the academic year, July through June) colours each cell by what the resident
rotates through — the four ward teams named by colour, a paired subspecialty unit (trauma/paediatrics,
hand/tumour, foot & ankle/sports, spine, arthroplasty), an out-of-department month, or free elective. A
one-click planner lays out a whole year under the programme's rules (first-years take anaesthesia,
rheumatology and trauma surgery for a month each; second-years take PM&R; third-years take three elective
months, at most two of them away at once, and act as team chief when no fourth-year is on that team;
fourth-years rotate subspecialties until February and then take free elective together through June), keeps
out-of-department months from colliding within a year group, balances team numbers, and reports whatever it
could not satisfy. Colours, abbreviations and unit types are editable. A **weekly roster** expands the current
rotation into individual sessions — OR lists, OPD clinics, ward rounds, conferences, on-call — generated
automatically from each service's weekly template, each carrying the staff member responsible for it. A
**presentation schedule** records who presents what, on which day, at what time, in which room, and which
attending moderates; recording a slide deck auto-links to its scheduled entry, so entries with no evidence
recorded stand out.

The staff member responsible for a session evaluates the resident at the end of it: three domain scores, an
entrustment level (1-5) and written feedback, with a per-staff board of sessions still awaiting evaluation
over the last 14 days. Those evaluations count toward each year's requirements and serve as workplace-based
assessment evidence for WFME areas 3, 5 and 7; the rotation schedule evidences 2.4, 2.5, 2.6 and 6.2, and the
presentation schedule 2.5 and 8.4. Subspecialty names are recorded and displayed in English throughout.

**Operative logbook from the OR queue system.** The queue demo in this same repository (`../index.html`)
carries its case data inside the page, so the portfolio can read it directly over one fetch on GitHub Pages;
a JSON/CSV export or a real `GET /api/cases?scope=all&includeClosed=true` endpoint work the same way. Cases
de-duplicate on the queue's own case id, and **patient names are deliberately not imported** — date, HN, age,
sex, diagnosis, operation, side, subspecialty, room, anaesthesia, ASA, duration and the primary surgeon are.
HN is masked in the table until you ask to see it.

The queue system records only the primary surgeon — there is no assistant field yet — so the portfolio adds
the attendance layer: names found on the case are matched against the resident roster, and where that fails
the rotation calendar suggests who was on that service that day, in bulk if wanted. Roles are primary
surgeon, first/second assistant, observer, each with a staff sign-off. Case counts by role feed the per-year
requirements and print as a per-resident logbook. For full automation the queue system would need to record
attendees per case (`attendees: [{userId, role}]`, or a populated assistant list).

**Installable on phones, same code as the web app.** The page ships a manifest, icons and a service worker
scoped to its own folder, so it installs from Android's install button or iOS's *Add to Home Screen*, opens
full-screen and runs with no signal. A diagnostics panel in settings reports install state, offline
readiness, and why a queue connection failed. Wrapping the same files with Capacitor gives a store/MDM
build, whose native HTTP layer also sidesteps browser CORS and mixed-content rules.

**Recommended shape when the queue is intranet-only but people need the portfolio from anywhere:** keep two
zones and let the intranet matter only at the moment cases are pulled. Users fetch cases while on hospital
wifi (works today, nothing to open up), or — once a shared backend exists — a small one-way sync agent
inside the hospital pushes de-identified cases outward over HTTPS, so nothing inbound is exposed. Opening
the queue system through a VPN or reverse proxy is the option to avoid. If the portfolio's server sits
outside the hospital, set the patient-data level to "store nothing", so only diagnosis, operation, role and
date leave the building, with the queue's own case id as the reference back.

**Reaching an intranet-only queue system** depends on where this page is hosted: same server as the queue is
frictionless (same-origin, existing session, no CORS); another intranet host needs CORS with credentials; a
public HTTPS host such as GitHub Pages cannot reach an HTTP intranet service at all (mixed content) and must
fall back to file import. Data still lives per-device; sharing one record across residents and staff would
need a backend, most sensibly an endpoint on the queue system's own server, which the single `store` layer
here is ready to sync against.

**Logbook sync** runs per user and automatically — on load, five seconds after any edit, every ten minutes
while pending, and the moment the device comes back online — with a status chip in the header. The payload is
three fields: operation date, diagnosis, operation (plus role if the user opts in), and the settings dialog
shows the exact JSON before it is enabled. A reference server under `sync-server/` documents the contract and
strips anything outside the agreed field list a second time on the way in.

**The Royal College logbook stays the system of record** — it needs films and operative notes uploaded by the
resident. This page does not duplicate it: it prepares the data (cases pulled from the queue, roles tagged in
a couple of clicks), tracks which cases are still not entered there, and prints a tick-box worksheet of
exactly those, so the official entry is quick rather than reconstructed from memory.

**Sign-in and least-privilege access.** Three roles: residents see only their own portfolio, activities,
logbook and EPA (shared rosters stay visible); staff see every resident in order to assess and verify;
programme admins manage registries, rotations, requirements, EPA topics and connections. Actions that matter
— sign-in, verification, assessments, imports, plan generation — land in a local audit trail. The checks run
in the browser, so this separates views on a shared device rather than authenticating anyone; the permission
layer is isolated so it can move to server sessions without touching the screens.

**EPA assessment** tracks an entrustment level per topic against a per-year target, by subspecialty, with
history, a programme-wide matrix for staff, and assessment linked to a case where relevant. The topics
currently shipped are placeholders — the real list drops in via CSV (`code, title, subspecialty,
year1..year4`) or JSON and replaces them wholesale.

Tested in headless Chromium: `.pptx`/`.pdf` ingestion, classification, persistence, exports and reports.
Requires a browser with `DecompressionStream` (Chrome/Edge 80+, Safari 16.4+, Firefox 113+).
